### Topic 1: Handling Form Submissions

**Coach:** Pleasure to work with you, David Jared! Let's start with **Topic 1: Handling Form Submissions**.  
Take a look at this snippet from your controller `src/controllers/projects.js` (lines 64–84):

```javascript
const processNewProjectForm = async (req, res, next) => {
    try {
        const errors = validationResult(req);
        if (!errors.isEmpty()) {
            errors.array().forEach((error) => {
                req.flash('error', error.msg);
            });
            return res.redirect('/new-project');
        }

```

In this code, you extract the data from `req.body`, and upon successful creation, you execute `res.redirect()` instead of `res.render()`. Why is it considered best practice to use `res.redirect()` (the Post-Redirect-Get pattern) when processing POST forms rather than rendering the page directly?

**Student (David):** `req.body` is what we send in the form—it is used to read whatever was typed by the user. The redirect sends the user to the next page to prevent re-submitting the POST request, and then renders the result safely.

**Coach:** Exactly right! `req.body` captures the payload sent in the HTTP request body via `express.urlencoded()`. Using the Post-Redirect-Get (PRG) pattern by redirecting to a GET route ensures that if the user refreshes their browser (e.g., presses F5), they won't trigger a duplicate form submission or create duplicate records in the database.

### Topic 3: Sessions and Flash Messages

**Coach:** Next, let's discuss **Topic 3: Sessions and Flash Messages**.  
Here is a snippet from your custom middleware in `src/middleware/flash.js` (lines 20–45):

```javascript
req.flash = function (type, message) {
    if (!req.session.flash) {
        req.session.flash = { success: [], error: [], warning: [], info: [] };
    }

    if (type && message) {
        req.session.flash[type].push(message);
        return;
    }

    // When queried without arguments, return all messages and clear storage
    const allMessages = req.session.flash;
    req.session.flash = { success: [], error: [], warning: [], info: [] };
    return allMessages;
};
```

Since HTTP is inherently stateless, why do we need session storage (`req.session`) to ensure a message like *"Organization added successfully!"* survives a `res.redirect()`, and why is it called a "flash" message?

**Student (David):** It is called "flash" because it only lasts for a moment: it renders in the view and disappears right away. To make the message survive the `res.redirect()` roundtrip, we use `req.session` so that we retain the response data that was sent and can display it based on the result.

**Coach:** Brilliant explanation! The session cookie ties the browser to server-side session memory across the two independent HTTP requests of the PRG pattern (POST then GET). It is called "flash" because the moment the EJS template invokes `flash()`, the messages are read and immediately cleared from the session, preventing them from reappearing upon page reload.

### Topic 4: Server-Side Validation

**Coach:** Finally, let's examine **Topic 4: Server-Side Validation**.  
Here are the validation rules you authored in `src/controllers/projects.js` (lines 11–32):

```javascript
const projectValidation = [
    body('title')
        .trim()
        .notEmpty().withMessage('Title is required')
        .isLength({ min: 3, max: 200 }).withMessage('Title must be between 3 and 200 characters'),
    body('description')
        .trim()
        .notEmpty().withMessage('Description is required')
        .isLength({ max: 1000 }).withMessage('Description must be less than 1000 characters'),
    body('location')
        .trim()
        .notEmpty().withMessage('Location is required')
        .isLength({ max: 200 }).withMessage('Location must be less than 200 characters'),
    body('date')
        .notEmpty().withMessage('Date is required')
        .isISO8601().withMessage('Date must be a valid date format'),
    body('organizationId')
        .notEmpty().withMessage('Organization is required')
        .isInt().withMessage('Organization must be a valid integer')
];
```

If we already have HTML5 client-side attributes like `required` and `maxlength`, why is server-side validation strictly necessary, and what purpose do sanitizers like `.trim()` and validators like `.isInt()` or `.isISO8601()` serve?

**Student (David):** Validating on the server is super necessary because it provides real security for the website; otherwise, anyone could send any arbitrary request and reach the server directly. The `.trim()` sanitizer cleans extra whitespace to prevent typing mistakes, and the other validators ensure the data format is strictly verified before storing.

**Coach:** Exactly, David! Client-side validation can easily be bypassed by disabling JavaScript or using tools like Postman or curl. Server-side validation with `express-validator` is the true security gatekeeper: it rejects malicious or malformed payloads, while `.trim()` and type validators sanitize and guarantee data integrity before reaching the database.
